## 1. 目标与边界

交付独立设计的 60 道 case 数据集，以及让这些 case 可加载、可执行、可验收、可保存评分证据的必要实现。新 case 严格采用四个必填字段和两个可选字段，不兼容旧 case，不导入旧 63＋37 评分政策。

不把现有 60 道题改名后视为新数据集。旧资料仅可提供候选来源；任何被选用的任务都必须重新制作、核验并通过新入库流程。

本计划中的具体目录、候选项目、题目方向和制作批次属于实施安排，不变更决策文档。候选项目已经查阅官方仓库入口，但具体 issue、起始 commit、可运行版本和依赖尚未核验。不能把以下选题表当作已存在的缺陷列表或合格 case 清单。

完整交付必须同时证明以下事项。

| 目标 | 所需证据 |
| --- | --- |
| 正确性 | 起点可复现、参考答案通过、错误与不完整答案被拒绝、事实与标签经核对 |
| 代表性 | 真实问题来源，或工程人员确认的真实项目请求；保留必要工程上下文 |
| 覆盖度 | 60 道题按决策中的十类场景分配，无缺项 |
| 多样性 | 不同项目、语言、故障机制、交付形式和验收方式，避免同一问题换参数重复 |
| 与评分衔接 | 真实产物、实际 diff、完整工具输入输出、验收结果和工程指标可被统一评分器读取 |

综合总分权重和成本归一化尚未确定，不阻塞任务验收与原始指标采集，但阻塞正式综合分排名。

## 2. 实施顺序

| 阶段 | 工作 | 产物 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| 1. 协议与执行基础 | 定义严格 case 校验、配置引用、工作区准备、约束检查、验收结果和执行记录协议 | 新加载器与最小执行、验收、记录链路 | 不需要旧 V2 适配即可执行新格式，系统错误与任务失败明确区分 |
| 2. 六道样题 | 制作缺陷修复、功能开发、迁移、依赖与构建、审查、研究各一题 | 六份完整 case 与各自入库证据 | 确定性、Judge、组合验收均可工作，评分输入不缺关键证据 |
| 3. 来源核验 | 搜索真实 issue、变更或合理新请求，固定版本并确认环境成本 | 60 个可制作的候选及各场景替补 | 每个候选有实际项目、可复现起点、明确完成条件；失败候选同场景替换 |
| 4. 第一批扩展 | 从 6 道扩展到 20 道，包含十类场景 | 20 道独立合格 case | 场景、语言和验收差异未迫使 case 增加字段 |
| 5. 第二批扩展 | 从 20 道扩展到 40 道 | 40 道合格 case | 完成批次复核，修复验收漏洞和环境问题 |
| 6. 第三批扩展 | 从 40 道扩展到 60 道 | 完整题库与覆盖清单 | 全部入库，场景数量准确，候选或待审核题不计入 60 |
| 7. 校准与交付 | 固定预算试跑、人工核验 Judge、冻结数据与运行配置、生成汇总 | 可复现数据集、质量报告、运行与评分说明 | 能运行完整 60 题，结果可追溯，未确定评分政策不被伪造为已确定 |

制作六道样题时即开始实际来源核验，不先编造样题再寻找仓库。其余候选核验可随基础实现推进，但不得绕过样题阶段批量生成全部题目。

## 3. 预计实现位置与职责

建议新数据集位于 `evals/dataset/`；现有 `evals/dataset-v2/` 在新数据集完成前保持为旧实现，不作为新格式的兼容入口。

```text
evals/dataset/
  dataset.json                 # 数据集版本与活动 case 路径
  execution.json               # 公共执行预算，制作样题后冻结
  runtimes/                    # 运行环境配置，由名称显式查找
  cases/
    CASE-001/
      case.json                # 仅使用已确认六字段结构
      instruction.md
      workspace/               # 还原后的完整初始工作区
      acceptance.json          # case 专属验收参数，不进入 Agent 工作区
      tests/                   # 有需要时保存可信验收程序
  preparation/                 # 来源、参考答案、错误答案与审核记录
  integrity.json               # 自动生成的完整性清单

packages/evals/src/dataset/    # 新加载、执行、验收、记录与汇总实现
```

`preparation/` 仅表示制作 case 时的资料目录，不是新增 case 字段，也不是执行器必须加载的依赖。完整性清单不重复嵌入 case。公共配置的具体字段在阶段 1 定义，避免提前扩大格式。

每道题的可交付目录可以包含可信验收程序，但 Agent 只取得 `workspace/` 中的内容与公开任务输入。目录分开本身不提供隔离，执行器还须限制 Agent 对私有资料与验收程序的访问。

运行环境可以复用，源码起点不能混用。制作和分发阶段可以复用压缩资产与依赖缓存；运行前还原为 case 指定目录。不得因为共享缓存让其他 case 的答案或状态进入当前工作区。

必要实现按职责划分，不复用旧评分语义。

| 实现 | 负责内容 |
| --- | --- |
| 加载器 | 六字段严格校验、引用解析、路径合法性、名称注册、完整性检查 |
| 执行器 | 每次新工作区、公开任务输入、环境准备、预算执行、工具调用和产物采集 |
| 验收器 | 显式接受 workspace、提交产物与必要执行证据，返回通过、失败或错误及逐项证据 |
| 执行记录 | 事件 ID、调用关联、输入输出、实际文件改动、完整性标记、工程指标 |
| 过程 Judge | 两个 0～4 等级、证据引用、无法评价原因，不能改写验收 |
| 统一评分器 | 验收结果、过程分与工程指标分开保存，重复运行与覆盖率汇总 |

现有模型与工具接口可作为基础能力使用；若证据采集缺失，需补充采集接口。不得用旧 `V2Task` 适配来代替新 case 实现，也不得将实际 diff 降级为哈希列表。

同一仓库的题目避免围绕同一缺陷或同一修复反复变体。初步来源分布覆盖 Python、TypeScript/JavaScript、Rust、Go；不以强凑语言比例牺牲任务质量。

| CASE-052 | 解释复杂输入的验证与序列化行为 | Pydantic | 可运行实例、源码依据、异常解释；事实检查＋Judge |
| CASE-053 | 解释并发查询下状态变化与取消行为 | TanStack Query 使用项目 | 固定复现轨迹、代码证据；事实检查＋Judge |
| CASE-054 | 解释多包构建的配置优先级与产物来源 | Vite 使用项目 | 实际配置链与产物证据；事实检查＋Judge |

工作区只读，回答保存在执行记录中或指定的可写输出目录，不能因为 `editable: []` 无法保存回答而放宽源码约束。

### 5.9 审查，3 道

| ID | 需求方向 | 候选真实项目 | 验收重点 |
| --- | --- | --- | --- |
| CASE-055 | 审查涉及权限与输入处理的真实变更 | Fastify 使用项目 | 已知关键问题、触发条件、影响与可验证证据；脚本＋Judge |
| CASE-056 | 审查事务或并发变更 | Django 使用项目 | 可复现竞争或回滚问题、关键遗漏、严重误报；脚本＋Judge |
| CASE-057 | 审查依赖或发布配置变更 | pnpm 使用项目 | 产物与依赖行为、风险证据及合理新发现；脚本＋Judge |

提供待审查的实际变更与基线资料；隐藏参考发现。不能把“发现数量多”直接作为完成度，也不能强制只报告参考列表。

### 5.10 研究，3 道

| ID | 需求方向 | 候选真实项目 | 验收重点 |
| --- | --- | --- | --- |
| CASE-058 | 判断重试策略是否适合实际 HTTP 写操作 | HTTPX 使用项目 | 幂等、失败语义、固定资料引用和未知项；事实检查＋Judge |
| CASE-059 | 比较实际 API 部署或安全配置方案 | FastAPI 使用项目 | 当前架构约束、方案取舍、风险与证据；事实检查＋Judge |
| CASE-060 | 为已有应用选择缓存与服务端渲染策略 | TanStack Query 使用项目 | 架构条件、缓存语义、替代方案与限制；事实检查＋Judge |

第一版使用固定版本源码与冻结资料，不依赖随时变化的网页结果。允许多个有充分证据的结论，参考答案以事实与必要论点为主。

| 功能开发 | 1 | 2 | 3 | 4 | 10 |

## 7. 每道 case 的制作与验证

1. 核实实际来源、用户请求和起始版本，记录任务是历史回放还是实际项目上的新请求。
2. 固定运行环境与资料，恢复完整工作区，验证无答案泄露。
3. 编写公开 instruction，明确交付、约束与必要条件，不披露隐藏样本或答案。
4. 编写验收参数与必要可信脚本，检查每项验收可追溯到公开要求。
5. 完成参考答案并保存实际产物；需要时制作不同合法实现或结论。
6. 制作针对关键条件的不完整、语义错误与绕过答案。负例覆盖核心要求，不能只用格式错误凑数。
7. 在干净环境重复还原与验收；缺陷修复确认对应 fail-to-pass 和 pass-to-pass 实际状态，其他场景使用合适初始状态检查。
8. 核验不修改的起点不会被当作完成；开放式任务需使用真实空回答与无依据回答，而非伪造文件。
9. 用固定预算执行 Agent，收集完整证据，分析环境或验收误判，不以成功率低直接证明题目困难。
10. 工程人员独立复核请求与验收；Judge 任务使用人工判定样本校准，记录审核身份与证据，不能把作者自检或模型评价声明成人工审核。

每道题必须有有效参考答案、实质性负例、来源与审核证据。资料存放在制作目录，不扩大 case，也不要求运行器为执行题目加载全部制作资料。

## 8. 执行记录与评分衔接

完整数据集不能只交付 60 个任务文件。阶段 2 即验证三条链路。

```text
case → 执行器 → 最终产物与必要状态 → 验收器 → 验收结果
case → 执行器 → 完整过程轨迹       → 过程 Judge → 两个等级与证据
     → 执行器 → 原始用量与时间     → 程序计算   → 工程指标
```

| 场景差异 | 必须支持的证据 |
| --- | --- |
| 代码修改 | 初始与最终文件、实际 diff、可信验收日志 |
| 集成与终端 | 服务、数据库、进程、Git 等必要状态，不能只保存源码 |
| 理解与研究 | 最终回答或报告、来源内容、读取与实验记录 |
| 审查 | 待审 diff、Agent findings、复现证据与代码位置 |
| 所有场景 | 实际输入、工具参数与完整结果、调用关联、缺失标记、用量与时间 |

所有验收器输出统一结果协议，但不同验收方式不被强制转换为 Node/TAP。逐项检查使用稳定 ID；退出码、缺失、跳过与运行错误不能混成通过。

过程 Judge 按决策中的两个维度评价，不能用验收失败直接推导过程零分。统一评分器按题平均重复运行，展示成功率、过程分、工程指标、场景覆盖与证据完整性；暂不生成尚未决定的综合总分。

## 9. 公共配置与人工工作

下列事项需在对应阶段具体确定。它们不进入每道 case，不影响六字段格式。

| 事项 | 确定时机 | 未确定时的处理 |
| --- | --- | --- |
| 运行环境及平台 | 阶段 1、样题准备 | 根据实际依赖选择固定配置，不假定 Windows 宿主与容器行为相同 |
| 公共执行预算 | 六道样题验证后、正式试跑前 | 记录实际消耗，不添加逐题难度倍率 |
| 验收结果与事件协议 | 阶段 1，样题检验 | 明确系统错误、任务失败、Agent 超时与证据缺失 |
| 验收 Judge 与过程 Judge 模型 | 样题校准前 | 可用桩验证接口；未运行真实 Judge 不宣称模型评价已通过 |
| Judge 校准与分歧处理 | 样题后、批次入库前 | 人工复核，不用自报置信度代替可靠性 |
| Agent 试跑范围与重复次数 | 阶段 7 前 | 固定配置并披露覆盖，单 Agent 结果不宣称跨 Agent 区分度 |
| 综合评分政策 | 样题与校准证据充分后 | 不继承旧权重，不生成正式综合排名 |

独立工程复核、Judge 人工校准和跨 Agent 试跑需要对应人员、模型配置与资源。可以先完成不依赖它们的环境、脚本、产物与接口工作；未完成这些要求的题目不得标记为正式入库。

## 10. 验证与交付清单

实现阶段执行必要的协议和行为验证，不能仅测试代码是否按自身实现返回预期。

| 验证 | 必须覆盖 |
| --- | --- |
| case 校验 | 未定义字段、缺少必填、未知配置、非法路径、只读与 protected 优先级 |
| 环境 | 干净还原、固定依赖、状态重置、缓存无答案、所需服务真实可用 |
| 验收 | 合法替代答案通过、实质错误被拒绝、缺失或跳过不通过、系统错误独立记录 |
| 完整性与隔离 | 初始资产改变可发现，Agent 无法读取答案或改写验收结果 |
| 记录 | 并行调用关联、输出引用、实际 diff、终端状态、缺失值、费用与耗时边界 |
| Judge | 有效证据 ID、人工校准、重复稳定性、匿名与篇幅偏差、无法评价 |
| 汇总 | 重复运行不改变题权、相同题目范围比较、覆盖率与系统错误披露 |

最终交付：

- 60 道通过入库核验的 case 与对应工作区、指令、验收参数。
- 运行环境配置与可复现资源准备方式。
- 新格式加载、执行、验收、执行记录、过程 Judge 和分维度汇总实现。
- 来源、参考答案、负例、独立审核与 Judge 校准资料。
- 数据集版本与自动生成的完整性清单。
- 60 道题的覆盖、重复与来源审核报告，以及固定预算试跑结果。
- 从干净环境运行单题和全部 60 题的操作说明。
- 明确未完成或未确定事项；缺少真实 Judge、独立审核或跨 Agent 试跑时不得声称这些部分已经完成。

阶段验收以实际证据为准。数据集完成前，文档状态保持为“实施中”或“候选”，不以文件数量达到 60 作为完成标准。
