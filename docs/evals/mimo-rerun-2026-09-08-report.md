## 4. 失败与异常

### I01：长上下文端口修复

任务失败，评分 64，耗时 127.2 秒、75.1k Token。Judge 认为 Agent 实际完成了逻辑修复，但 Oracle 只接受 `port > 0`，Agent 使用了语义等价的 `>= 1`。这是一个需要继续放宽的代码语义 Oracle，不应直接判定为模型逻辑失败。

### O01：Legacy 重构

任务失败，Judge 发生连接错误，断言也未通过。由于 Judge error，当前无法把它可靠归因到 Agent 能力；需要单独重跑确认。

### S01/S02：本地研究

两个任务的确定性断言均未满足，但 Judge 认为 Agent 的最终总结在语义上准确。当前主要问题是研究结论没有稳定落盘为断言要求的 `research.md` 内容，属于“口头总结正确、工程产物不完整”的失败类型。

### U04：缓存使用分析

任务失败，评分 70。Judge 认为 Agent 正确说明了无法通过当前工具访问所需缓存使用数据；但任务本身要求产出缓存使用分析，因此仍记录为任务未完成。

### R01：长上下文成本异常

任务通过，但耗时 564.7 秒、消耗 858.5k Token。相比之前约 300 秒、116.6k Token，延迟和 Token 消耗均显著恶化。这更像 Mimo 服务或 Agent 执行轨迹异常，不能作为能力提升的正面信号。

## 5. 结论

在相同的 48 个任务集合上，DreamCode 的确定性通过率从 83.33% 提升到 91.67%，平均主评分从 88.73 提升到 90.71，说明任务完成能力整体有进步。

但工程质量没有同步改善：本轮 P95 延迟 127.24 秒，总 Token 接近 300 万，R01 出现 858.5k Token 的极端异常，且 Judge 出现 1 次连接错误。因此当前结论是：

> Agent 的任务成功能力有明显提升，但执行成本、长上下文稳定性和研究类任务的产物落盘能力仍不稳定，暂时不能称为全面提升。

下一步应优先：

1. 校准 I01 的 `>= 1` 与 `> 0` 等价代码断言；
2. 单独重跑 O01，排除 Judge 连接错误；
3. 分析 R01 的 858.5k Token 轨迹；
4. 强化 S01/S02 的“必须写入目标文件”约束和 Agent 自检；
5. 对同一批任务进行至少 3 次重复运行，才能判断稳定性改善。
