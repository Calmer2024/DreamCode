# DreamCode 桌面 UI HTML 复刻设计

## 1. 目标

在不修改现有 Electron/React 桌面端代码的前提下，使用视觉伴侣创建一个独立、可交互的 HTML Demo，完整复刻当前已安装 DreamCode 桌面版的界面。团队将在该 Demo 中共同调整 UI；最终确认后的 HTML 与设计规则将作为桌面端 UI 重构的实现参照。

第一版只建立忠实基线，不主动美化、重排或修正当前 UI。

## 2. 数据与隐私

- 使用接近真实使用场景的内置示例数据。
- 不复制本机真实工作区名称、会话标题、对话内容、API Key 或其他配置数据。
- Demo 不连接 DreamCode Runtime，不执行模型请求、工具调用、文件修改、配置保存或回滚。

## 3. 复刻方案

采用单文件交互式 HTML 状态机：

- 一个产品画布承载完整 DreamCode 桌面界面。
- 一个与产品画布视觉隔离的 Demo 控制区负责切换状态。
- 公共布局和组件只维护一份，避免多个静态页面逐渐不一致。
- 每轮视觉修改生成新的视觉伴侣版本，以便比较和回退。

不直接复用现有 React Renderer。HTML Demo 必须能够脱离 Electron 与 IPC 独立展示，便于自由调整信息架构和视觉表现。

## 4. 基准画布与布局

- 默认画布：`1440 × 900`，对应当前桌面窗口默认尺寸。
- 最小验证尺寸：`1024 × 700`，对应当前桌面窗口最小尺寸。
- 主结构：`264px` 左侧栏与自适应主内容区。
- 主内容区由任务标题栏、可滚动时间线和底部悬浮输入框组成。
- 第一版严格参照当前实现的字体、颜色、间距、边框、圆角、阴影、图标尺寸和组件位置。
- Demo 控制区不得出现在产品画布内部，也不得被误认为 DreamCode 正式功能。

## 5. 组件范围

HTML Demo 必须覆盖：

- 品牌区、主导航、工作区和会话列表、设置入口。
- 任务标题、工作区选择以及详情、终端、文件变更入口。
- 欢迎状态和其他空状态。
- 用户消息、助手消息、工具调用、文件变更、生命周期状态与普通事件时间线。
- 悬浮输入框、运行模式选择、模型选择、发送和停止状态。
- 模型与配置弹窗。
- 工具审批弹窗和问题回答弹窗。
- 任务证据抽屉及 Diff、终端、事件、会话标签页。
- 文件回滚二次确认。
- 普通错误提示、配置加载失败和恢复操作。

## 6. 状态与本地交互

Demo 控制区必须能够切换：

- 欢迎页。
- 未选择工作区。
- 未配置模型。
- 历史会话。
- 正在启动、运行中、已完成、失败和已停止。
- 配置、审批与问题弹窗。
- Diff、终端、事件和会话抽屉。
- 文件回滚确认。
- 普通错误与配置加载失败。

侧栏会话、输入框、选择器、抽屉标签和弹窗按钮提供本地演示交互。交互只改变 Demo 内存状态，不产生外部副作用。

## 7. 响应式与可访问性

- `1440 × 900` 下优先保证与当前桌面端一致。
- `1024 × 700` 下不得出现关键控件重叠、遮挡或不可操作。
- 更窄尺寸仅用于观察降级表现，不作为首轮桌面端验收目标。
- 使用语义化按钮、输入框、选择器、对话框和标签页。
- 保留键盘焦点反馈、可读标签以及必要的 ARIA 状态。

## 8. 验收标准

第一版忠实复刻通过以下条件验收：

1. 当前桌面端的所有主要组件和关键状态都能在 Demo 中找到。
2. `1440 × 900` 下的结构、比例、视觉层级和组件位置与当前实现一致。
3. 所有状态可通过 Demo 控制区稳定切换。
4. `1024 × 700` 下无关键内容重叠、裁切或无法操作。
5. Demo 不读取真实用户数据，也不触发任何 DreamCode Runtime 或文件系统操作。

忠实基线经用户确认后，后续视觉修改都在该 Demo 上迭代。只有用户明确确认最终 Demo 后，才开始修改 Electron/React 桌面端 UI。

## 9. 最终实现参照

最终确认后，从 HTML Demo 提炼并固定：

- 色彩与语义状态。
- 字体层级。
- 间距与布局网格。
- 边框、圆角和阴影。
- 组件尺寸与交互状态。
- 时间线、弹窗、抽屉和输入框行为。
- `1440 × 900` 与 `1024 × 700` 的响应式规则。

这些规则和最终 HTML 共同构成桌面端 UI 重构的实现依据。
